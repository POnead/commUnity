## Findings

### QA-O01 — Official profile: duplicate element ids, two unlabelled fields (Medium, Accessibility)
- Observed: on `#/official/profile`, `#email` was used by both the read-only sign-in email and the "Change sign-in email" field, and `#currentPassword` by both the email-change password and the password-change password. `document.querySelectorAll('[id]')` reported two duplicate ids; the second input in each pair had no associated label (its `labels` list pointed at the first field), so screen readers announce an unnamed edit field.
- Root cause: the shared (official) profile branch reused `name` as the id, while the administrator branch already used unique ids.
- Fix applied: gave the four fields explicit unique ids (`profile-sign-in-email`, `change-email-address`, `profile-email-current-password`, `profile-current-password`) in the official branch, mirroring the administrator branch. Applied the same ids to the resident branch, which had the identical duplication.
- Verified: duplicate-id sweep now returns `[]` and the unlabelled-field sweep returns `[]` on the official profile page.

### QA-O02 — Concern queue: "All reports" shows 0 although a resolved report exists (Low, UX/Copy)
- Observed: the official concern queue rendered `All reports 0` next to an empty state, but the same page showed "Resolved concerns · 1 marked as addressed". The filter intentionally counts only non-resolved reports (resolved are shown in a separate section), so the label contradicted the number.
- Fix applied: renamed the official filter label from "All reports" to "Open reports" (`officialReportFilters`). The resident report filters still say "All reports" because they do include resolved.
- Verified: filter row now reads `Open reports 0 / Submitted 0 / Under review 0 / In progress 0`, and the resolved section still renders.

### QA-O03 — Informational modal opens without moving focus into the dialog (Low, Accessibility)
- Observed: double-clicking a calendar day with events opened the "Event details" dialog, but `document.activeElement` stayed on `BODY`; the render code only focused a modal when it contained an input/select/textarea. Keyboard users can still Tab in, but screen-reader browse mode does not announce the dialog on open.
- Fix applied: when no form field exists, focus the dialog title; added `tabindex="-1"` to `#modal-title` and fall back to it in `render()`.
- Verified: `document.activeElement` is now `H2#modal-title` inside `section.modal[role=dialog]`; Escape still closes and returns to the page.

### QA-O04 — Repeated hotline actions have identical accessible names (Low, Accessibility)
- Observed: each hotline card exposed `Call Now`, `Copy` and `Suggest correction` with the same accessible name, so a screen reader hears "Copy, button", "Copy, button" with no way to tell which number is copied.
- Fix applied: item-specific `aria-label`s that preserve the visible text — `Call Now: <hotline> at <number>`, `Copy <hotline> number`, `Suggest correction for <hotline>`.
- Verified: DOM audit shows distinct names per card; Lighthouse reports no label-content-name-mismatch failures.
