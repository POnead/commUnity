## Findings

### QA-001 — Validation/error message persists across public SPA routes (Medium, Functional/UX)
**Confirmed, reproduced twice in both directions.**

- Observed: after a registration validation failure ("The passwords do not match."), navigating in-app to `#/login` still shows that registration error at the bottom of the sign-in page. After a failed sign-in ("Those sign-in details do not match an active account."), navigating in-app to `#/register` still shows the sign-in error there. It also persists on `#/forgot-password`.
- Repro: load `/` (lands on `#/login`) → go to `#/register` → fill name/email/area, set password `StrongPass123!` and confirm `Different123!` → click **Create account** → error appears, no POST → change hash to `#/login` → stale registration error still rendered. Reverse direction reproduced the same way via a failed sign-in.
- A hard reload clears it, confirming it is in-app state, not server output.
- Impact: users see an error that does not apply to the page they are on; misleading during sign-in or registration. Workaround: reload.
- Proposed fix (not applied): clear the shared error/status region on every route change or scope the error to the form that produced it.

### QA-002 — `/api/map-config` 401 on unauthenticated public pages (Low, Console)
- Observed: on first load and again during the session, `GET http://127.0.0.1:8768/api/map-config` returns 401 and Chromium logs `Failed to load resource: the server responded with a status of 401 (Unauthorized)`.
- Context: README says the Maps key is delivered only to signed-in sessions, so the endpoint is correctly auth-gated; the problem is that public pages call it while signed out and surface the 401 in the console.
- Impact: console noise that masks real errors. Workaround: none needed for the user.
- Proposed fix (not applied): skip the map-config fetch when there is no authenticated session, or handle 401 silently.

### QA-003 — Expected validation failures logged as console.error with stack traces (Low, Console)
- Observed: a password mismatch and a wrong-credential sign-in each produce entries such as `CommUnity could not complete login-form. Error: Those sign-in details do not match an active account.` with a full stack trace from `app/main.mjs:4877`.
- Impact: normal user mistakes are indistinguishable from genuine crashes in console monitoring. Workaround: none needed for the user.
- Proposed fix (not applied): route expected validation failures to a non-error log level or a dedicated user-facing status channel.
